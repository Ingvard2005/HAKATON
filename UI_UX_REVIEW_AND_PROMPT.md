# CallMind: разбор UI/UX и промпт для переработки

Дата: 6 октября 2026 года. Основание: сохранённый скриншот текущего обзора и код frontend/app.py. Дополнительных новых скриншотов в последнем сообщении нет. Видимые проблемы помечены «скрин», поведение других экранов — «код». Это экспертная проверка, не пользовательское исследование; скорость действий, контраст и доступность ещё требуется измерить.

## Цель интерфейса

Менеджер с 30–40 звонками в день должен быстро ответить: что сделать сейчас, по какому клиенту, до какого срока, откуда взялась договорённость и сохранена ли она в CRM. Руководитель должен видеть соблюдение сроков и подтверждённые результаты сделок.

## Как должна выглядеть панель

- Шапка: «Обзор» + дата/период + «Добавить звонок».
- Компактные показатели: просрочено, сегодня, требуется проверка, в работе.
- «Требует внимания»: ближайшие действия, неподтверждённые договорённости, ошибки синхронизации; у каждого элемента кнопка действия.
- Поиск и фильтры: клиент, срок, статус, ответственная сторона, приоритет. На телефоне вторичные фильтры раскрываются отдельно.
- Список: действие, клиент, срок, сторона обязательства, приоритет, состояние проверки/CRM. Детали открываются без потери фильтров и положения в списке.
- Панель деталей: цитата и запись, описание, редактирование, связь со звонком и сделкой, состояние каждого внешнего сервиса, журнал изменений.
- Аналитика: отдельный экран по спецификации ANALYTICS_SPEC.md. Не перегружать оперативный обзор графиками.

## Готовый промпт для редактирования

Ниже текст для передачи модели вместе со скриншотом, этим проектом и ANALYTICS_SPEC.md. Скриншот является визуальным контекстом; код — источником фактических возможностей.

```text
Ты продуктовый UX/UI-дизайнер и разработчик интерфейса CallMind.
Переработай существующую панель для менеджера по продажам, который делает 30–40 звонков в день и должен не терять договорённости. Используй приложенные скриншоты и файлы проекта. Разделяй наблюдаемое на скриншоте, подтверждённое кодом и гипотезы. Не заявляй, что проведено пользовательское исследование.

Сначала представь короткий список проблем с приоритетом, пользовательским последствием и исправлением. Затем реализуй изменения интерфейса в текущем проекте и проверь их. Сохрани работающие сервисы, API, данные, экспорт, историю правок и функции AI. Не подменяй реальный функционал декоративными кнопками. Для новой серверной возможности явно укажи зависимость; не показывай выдуманные показатели в рабочем интерфейсе.

Главные задачи:
1. Сделать рабочие задачи видимыми на первом экране. Компактная шапка, поиск и фильтры; заметная кнопка «Добавить звонок». Экспорт — вторичное действие.
2. Разделить статус, срок и ответственную сторону на независимые фильтры. Убрать перегруженную полосу из шести вкладок. Сделать видимыми «Просрочено», «Сегодня» и «Требует проверки». По умолчанию сортировать по срочности.
3. На desktop сделать компактный список или таблицу договорённостей. На телефоне использовать карточки с действием, клиентом, сроком, статусом и кнопкой. Детали не должны занимать весь список.
4. Добавить понятные детали договорённости: цитата, переход к записи при доступных временных отметках, звонок, клиент, связанная сделка, правки и человеческий журнал изменений. Не придумывать диапазоны цитат, если их нет.
5. Разделить «чья договорённость» и «кому назначена задача в CRM». Для неопределённых данных показывать «Нужна проверка» с причиной. Не рисовать произвольные проценты уверенности AI.
6. Сделать редактирование логичным: скрыть/отключить время при сроке без времени, поля срока при отсутствии срока. Добавить сохранено/ошибка/несохранённые изменения. Действия на одной задаче должны согласованно обновлять все её представления.
7. Показать Bitrix24 и Google Calendar отдельно: не подключено, настроено и ещё не проверено, синхронизируется, подтверждено, нужна повторная проверка. Сохранять сообщения обоих сервисов. Не выдавать локальное сохранение за успешную отправку в CRM. При автосинхронизации объяснять, что будет обновлено.
8. Навигация: Обзор, Звонки, Клиенты, Сделки, Аналитика, Настройки. Новые разделы должны быть связаны с данными, а недоступные сценарии обозначены. Не добавлять корпоративные роли без реальной модели доступа.
9. Добавить аналитику согласно ANALYTICS_SPEC.md: соблюдение договорённостей и результаты сделок — отдельные блоки. «Выполнено» не означает «сделка выиграна». Прогноз риска не означает «сделка проиграна». Успешная/проигранная сделка берётся из CRM или подтверждается человеком, с источником и временем.
10. Сохранить спокойный деловой стиль: светлый фон, тёмный читаемый текст, красный акцент МТС для основных действий, семантические цвета для состояний, достаточный контраст, видимый focus. Не полагаться только на цвет.

Ограничения:
- Проект сейчас использует Streamlit. Сначала работай в нём, без автоматической смены стека. Если требуемая панель деталей или навигация ограничена Streamlit, предложи и реализуй ближайший рабочий вариант, честно пояснив ограничение.
- Основные действия на мобильном имеют удобную область нажатия, ориентир 44 px. Проверь ширину 390 px, desktop 1280 px, длинные имена и описания, отсутствие сроков, пустой список, ошибку AI, ошибку одного внешнего сервиса, неподтверждённый результат, несохранённые правки.
- Согласуй правила «встреча → событие», «задача → напоминание по сроку». Не меняй семантику календаря только визуально.
- Не отправляй записи и данные клиентов во внешние системы ради дизайн-анализа. Для проверки используй отдельную тестовую базу и сетевые заглушки.
- Не придумывай рост продаж, сэкономленные часы и причины потери сделки. Если данных нет, покажи «Недостаточно данных» и объясни, что требуется.

Критерии готовности:
- Менеджер видит срочную задачу и доступное действие без длинной прокрутки.
- Пользователь находит нужную договорённость по клиенту, проверяет цитату, исправляет срок и понимает, куда сохранены изменения.
- На телефоне нет горизонтального переполнения всей страницы и скрытого единственного пути к важному действию.
- Аналитика показывает период, определения и доступные данные; любой показатель ведёт к соответствующим записям.
- Данные и существующий функционал сохранены, подходящие проверки проходят, приложены итоговые скриншоты и перечень оставшихся зависимостей.
```

## Проверка доступности

Точный контраст по картинке не измерялся. Для обычного текста целевой минимум WCAG AA — 4.5:1; для крупного — 3:1. Минимальный размер цели в WCAG 2.2 AA — 24×24 CSS px с оговорёнными исключениями; 44 px выше — выбранный ориентир удобства мобильного продукта, а не утверждение о минимуме AA. Источники: [контраст](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum.html), [WCAG 2.2](https://www.w3.org/TR/WCAG22/).
