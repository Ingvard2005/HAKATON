# CallMind: аналитика договорённостей и сделок

Это спецификация, сформированная до переработки панели. Реализованный объём и проверки описаны в [UI_REDESIGN_RESULT.md](UI_REDESIGN_RESULT.md). Обновление CRM: [CRM_SYNC_SPEC.md](CRM_SYNC_SPEC.md) — добавлены импорт текущих стадий/результатов и дальнейшая сверка связанных сделок. Полная история переходов до подключения и корпоративная модель доступа остаются зависимостями. Ниже сохранены определения и предложения по дальнейшему развитию.

## Основной принцип

Разделить три результата:

1. Выполнение договорённости — действие сделали или не сделали вовремя.
2. Результат сделки — выиграна, проиграна, ещё в работе.
3. Возможная связь — до потери сделки были просрочки; причина подтверждена менеджером или только предложена AI.

«Менеджер отправил КП» не означает продажу. «Клиент отказался» не означает, что менеджер нарушил обещание. Пропущенный срок не означает автоматическую потерю сделки.

## Блоки экрана «Аналитика»

### 1. Договорённости

Фильтры: период, клиент, приоритет, тип. Менеджер/команда — после добавления соответствующей модели и доступа.

| Показатель | Определение | Данные / ограничение |
|---|---|---|
| Новые договорённости | Число созданных в выбранном периоде | created_at; показывать период создания |
| Выполнено | Число переходов к фактическому выполнению в периоде, уникальные договорённости по выбранной политике повторного открытия | completed_at плюс история статусов; не считать старые done без даты как выполненные сегодня |
| Просрочено сейчас | Активные договорённости, чей подтверждённый срок уже прошёл | Текущий снимок на указанное время; не выдавать за историческую просрочку за месяц |
| Выполнение в срок | Выполненные к сроку / все учитываемые договорённости со сроком в выбранном периоде | В знаменателе остаются невыполненные просроченные; отменённые исключаются по явной политике, без срока — отдельно |
| Без срока | Активные договорённости с deadline=null | Полезный отдельный список, не ошибка по умолчанию |
| Требуют проверки | Неопределённый ответственный, недоступная цитата, ручная отметка проверки | Состояние проверки ещё нужно хранить явно |

Для метрики «в срок» зафиксировать отчётный due_at: срок, подтверждённый на начало периода; для новых задач — первый подтверждённый срок. Переносы показывать отдельно с причиной и временем. Перенос уже просроченного срока не должен стирать факт нарушения. Если нужной истории/исходного срока нет, показывать неполное покрытие, не подставлять нули.

Срок без времени означает конец дня в согласованном часовом поясе. Задачи, срок которых ещё не наступил, не включать в финальную оценку «в срок» до наступления срока; для текущего незавершённого периода указывать дату среза и предварительность.

Графики MVP: динамика новых и выполненных договорённостей по дням; список просрочек по клиентам; доля выполнения в срок с количеством наблюдений. Каждый показатель открывает исходный список, на котором он рассчитан.

### 2. Сделки

Да, добавить фиксацию успешных и проигранных сделок. В UI нейтральный термин — «Проиграна»; «Сорвана из-за невыполненной договорённости» — отдельная подтверждённая причина.

Минимальный жизненный цикл: «В работе», «Выиграна», «Проиграна». Пользовательские стадии воронки CRM сохраняются дополнительно. Вернувшаяся в работу сделка использует прежний ID и историю, а не создаётся заново.

В карточке сделки: название, клиент, менеджер, стадия, сумма и валюта, ожидаемая/фактическая дата закрытия, следующий шаг, связанные звонки и договорённости, источник и время обновления.

При ручном закрытии: результат, фактическая дата, причина проигрыша (обязательна при проигрыше), комментарий. Сумма допустима неизвестной. История хранит предыдущий результат, автора, источник и время. Изменять итог сделки отдельным действием, не кнопкой выполнения задачи.

| Показатель | Определение |
|---|---|
| Выигранные | Уникальные сделки с подтверждённым успешным закрытием в периоде |
| Проигранные | Уникальные сделки с подтверждённым проигрышем в периоде |
| Доля побед среди закрытых | won / (won + lost) × 100%; при отсутствии закрытых — «Нет данных», не 0% |
| Сумма выигранных сделок | Сумма подтверждённых сумм выигранных сделок отдельно по валютам; неизвестные суммы и их число показаны отдельно |
| Средняя сумма выигранной сделки | Известная сумма / число выигранных сделок с известной суммой, отдельно по валюте |
| Время до закрытия | Медиана closed_at − created_at по закрытым сделкам с корректными датами |
| Причины проигрыша | Распределение подтверждённых причин с числом сделок и «Не указано» для импортированных данных |

Сумма выигранных сделок — договорной объём, не оплаченная выручка. Сумма проигранных возможностей — не бухгалтерский убыток. Для денег нужны валюта и политика конвертации; в MVP показывать валюты отдельно. Не суммировать BYN, RUB и USD одним числом.

Выбор периода по умолчанию — дата подтверждённого закрытия. Импортировать историю переходов для корректных исторических отчётов: дата планового закрытия CRM не доказывает фактическое закрытие. Если доступны только текущее состояние и плановая дата, показывать текущий снимок и неполноту данных.

При повторном открытии считать состояние на конец выбранного периода и последний актуальный подтверждённый переход; правила дедупликации явно указать. Просроченная задача в сделке с двумя звонками не должна превращаться в две потерянные сделки.

### 3. Причины потери и связь с договорённостями

Предлагаемый справочник: цена; конкурент; нет бюджета; потребность исчезла; условия не подходят; несоблюдение срока; отсутствие последующего контакта; другое. Причина из AI — предложение; в отчёте подтверждённых причин учитывается после проверки человеком или как подтверждённое поле CRM.

Полезные дополнительные показатели:

- Выигранные/проигранные сделки с просроченными обязательствами до закрытия.
- Сделки без следующего шага, с указанием даты последнего контакта.
- Активные сделки с обязательствами, требующими проверки.
- Подтверждённые потери из-за срока или отсутствия контакта.

Использовать подпись «У этих проигранных сделок были просрочки», если известна только последовательность событий. Для подписи «Потеряны из-за просрочки» нужны подтверждённая причина и связь с конкретным обязательством.

На маленьком наборе не делать вывод о росте продаж или влиянии CallMind. Сравнение до/после требует сопоставимых периодов, состава клиентов, воронки и объёма наблюдений; отдельная гипотеза, не автоматический KPI.

### 4. Качество сервиса

Для менеджера: звонки с ошибкой обработки, неподтверждённые результаты и ошибки CRM/календаря, с кнопками исправления. Для администратора: время обработки, доля успешных синхронизаций и последнее обновление.

Доля ручных правок показывает частоту корректировок, но не измеряет точность модели. «90% распознавания ключевых фраз» требует отдельного эталонного набора. Сэкономленные часы выводить только при согласованном измерении ручного времени и времени проверки AI; количества звонков недостаточно.

## Источник сделок: Bitrix24

Текущий код импортирует сделки связанного клиента, стадии и их семантику, сумму/валюту, менеджера, результат/источник/время. Сделки сверяются из CRM в CallMind; обратное изменение стадии не реализовано. Исторические переходы до первого импорта не восстанавливаются. MOVED_TIME используется при наличии; иначе DATE_MODIFY помечается как время обновления, которое не доказывает точный момент закрытия.

Для расширения нужны: права чтения CRM, внешний ID сделки, идентификатор воронки, стадия и её семантика, контакты/клиент, ответственный, сумма/валюта, история закрытия, время последней синхронизации. Учитывать пользовательские стадии по семантике, а не только по названию «Успех».

Официальная документация: [методы сделок](https://apidocs.bitrix24.ru/api-reference/crm/deals/), [поля CRM](https://apidocs.bitrix24.ru/api-reference/crm/main-entities-fields.html), [семантика стадий](https://apidocs.bitrix24.com/tutorials/crm/how-to-get-lists/how-to-get-stages-with-semantics.html).

Для демонстрации без CRM можно создавать сделки вручную. Обязательная маркировка источника: «Введено вручную» или «Bitrix24». Для импортированной сделки CRM — основной источник результата; ручная локальная правка не должна молча перезаписывать CRM. Внешняя запись потребует отдельного согласованного действия и прав.

## Минимальная модель данных

```text
Deal
  id, client_id, title, owner_id
  outcome: open | won | lost
  stage_id, pipeline_id
  amount: decimal/null, currency
  created_at, expected_close_at, actual_closed_at/null
  loss_reason, loss_comment
  source: manual | bitrix24
  external_deal_id, synced_at

DealOutcomeEvent
  deal_id, previous_outcome, new_outcome
  occurred_at, recorded_at, actor_id, source, reason

CallDealLink
  call_id, deal_id

AgreementDealLink
  agreement_id, deal_id

AgreementReview
  agreement_id, state, reasons, reviewed_by, reviewed_at
```

Один клиент может иметь несколько сделок; автоматическая привязка по одному имени недопустима. Отдельный звонок может обсуждать несколько сделок, поэтому предусмотреть явные связи. Для сумм использовать decimal; факт выполнения задачи и итог сделки хранятся независимо.

Нужны также история подтверждённых сроков, причины переносов, отмена задачи и история выполнения/возврата. Существующий completed_at обнуляется при возврате в работу; для исторической аналитики одного текущего значения недостаточно.

## Объём для хакатона

1. Экран «Сделки»: список, карточка, создание/привязка, подтверждённое закрытие и причина проигрыша.
2. Экран «Аналитика»: период, выиграно, проиграно, доля побед среди закрытых, сумма выигранных по валютам, причины проигрыша.
3. Блок договорённостей: текущие просрочки и задачи на сегодня; «в срок» только после появления достаточной истории дат.
4. Связь звонка/обязательства со сделкой; переход из KPI к исходным записям.
5. Импорт Bitrix24 отдельным этапом, с маркировкой времени обновления и неполного покрытия.

Не включать в первый релиз прогноз финансовых потерь, проценты «достоверности» без калибровки, влияние AI на продажи и рейтинг сотрудников по недоступным данным.

## Сценарии проверки

- Нет закрытых сделок: доля побед не вычисляется, отображается «Нет данных».
- Две победы и один проигрыш: доля побед среди закрытых 66.7%; активные не входят в знаменатель.
- Повторный импорт одной сделки: количество не увеличивается.
- Две валюты: суммы показаны раздельно.
- Выполненная договорённость в открытой сделке: количество выигранных не меняется.
- Проигрыш по цене при выполненных обязательствах: не относится к потерям из-за сроков.
- Просрочка без закрытия сделки: предупреждение, не проигрыш.
- Возврат сделки/задачи в работу: предыдущие события сохраняются, текущий и исторический отчёты не смешиваются.
- Нет фактической даты закрытия/старого срока: показатель помечен неполным; плановую дату нельзя подставлять вместо факта.
