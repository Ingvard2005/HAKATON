# CallMind: интерфейс и интеграции

Google Calendar: реализованы перенос после подтверждения, двусторонняя сверка связанных событий, отдельная автосинхронизация, конфликты и защита версии события. Реальное создание/изменение/отмена и доставка уведомления на телефон проверены на синтетических событиях. Подробности и ограничения: [CALENDAR_SYNC_SPEC.md](CALENDAR_SYNC_SPEC.md). Автосинхронизация по умолчанию выключена; первый перенос всегда явный.

В интерфейсе доступны Обзор, Звонки, Клиенты, Сделки, Аналитика и Настройки. Компактный список договорённостей открывает отдельный экран деталей, на телефоне строки превращаются в карточки. Есть независимые фильтры статуса, срока и стороны, ручная проверка AI, черновики правок в текущей сессии, журнал изменений, CSV, PDF и ICS. AI загружается только при запросе анализа.

PDF в блоке «Экспорт текущего списка» содержит отфильтрованные договорённости, дату выгрузки, часовой пояс и фильтры. Формат A4 в альбомной ориентации: повтор заголовков таблицы, номера страниц, красная полоса и векторный символ яйца. Генерация локальная, библиотека `reportlab==5.0.1` указана в requirements.txt; русский шрифт DejaVu и его лицензия находятся в assets/fonts. Пустой список экспортируется с пояснением, без выдуманных записей.

## Локальный запуск

Из корня проекта с установленным Python 3.12:

```powershell
python -m venv .venv-ui
.venv-ui/Scripts/python.exe -m pip install -r requirements-ui.txt
.venv-ui/Scripts/python.exe -m streamlit run frontend/app.py --server.address 127.0.0.1
```

Открыть http://localhost:8501. В текущей рабочей папке отдельное окружение `.venv-ui` уже подготовлено. Оно не заменяет существующее `.venv`.

Для анализа аудио дополнительно установить `faster-whisper` и `google-genai` или подключить реализацию Qwen в `services/llm.py`. Текущий AI-код сохранён. Whisper может загружать веса при первом запуске. Интерфейс, история и редактирование работают без этих AI-пакетов и API-ключа.

Не перезаписывайте существующий `.env`: перенесите нужные переменные из `.env.example`. Секреты не добавляйте в Git. Новые таблицы метаданных, настроек, правок и синхронизации создаются автоматически, существующие таблицы/записи не удаляются. Перед первым запуском на рабочих данных сохраните резервную копию SQLite.

## Bitrix24

Актуальный OAuth-сценарий переноса клиентов и задач, выбора сделок и двусторонней сверки описан в [CRM_SYNC_SPEC.md](CRM_SYNC_SPEC.md). В настройках появился отдельный переключатель `crm_auto_sync` (по умолчанию выключен). Фоновая сверка работает только с уже связанными записями. Ниже сохранена совместимая настройка старого вебхука, которая обслуживает задачи без нового сопоставления клиентов.

1. В тестовом портале создать входящий вебхук с доступом к задачам (`task`) от сотрудника, имеющего права создавать и редактировать задачи. Доступность REST/вебхуков зависит от условий вашего портала; проверить до демонстрации.
2. Задать `BITRIX24_WEBHOOK_URL` (базовый URL вида `https://PORTAL/rest/USER_ID/SECRET/`) и `BITRIX24_RESPONSIBLE_ID` (ID сотрудника, которому назначаются задачи).
3. Для старого вебхука при необходимости задать `BITRIX24_CRM_BINDING`, например `C_7` или `D_10`. Это статическая привязка только для демо. OAuth с правами CRM использует сопоставление по телефону/email и отдельную выбранную сделку, а не эту переменную. Не используйте одну статическую привязку для разных клиентов.
4. Перезапустить приложение. В карточке договорённости сохранить исправления, нажать «Подтвердить», затем в блоке «CRM и календарь» выбрать «Перенос» (оба сервиса), «Перенос в CRM» или «Перенос в календарь». Без подтверждения отправка заблокирована также на сервере.

В Bitrix24 создаётся задача сотрудника, даже если обязательство принадлежит клиенту: сторона обязательства явно указана в описании. В OAuth-сценарии исполнитель выбирается отдельно для каждой задачи; по умолчанию — вошедший пользователь.

Сохраняется ID задачи; последующий ручной перенос обновляет её, включая локальные правки и статус выполнения / возврата. Сохранение, анализ и выполнение сами по себе ничего не отправляют. Старое `auto_sync=true` игнорируется; настройка и API всегда возвращают false. После неподтверждённого создания повтор блокируется, чтобы не создать дубль: проверить портал и ввести ID уже созданной задачи. Если задача не была создана или процесс завис в `syncing`, состояние нужно сверить; автоматическое сбрасывание без проверки опасно. Ошибки не выводят секретный URL.

## Сделки и аналитика

Сделки вводятся вручную и явно связываются со звонками / договорённостями одного клиента. При закрытии нужны фактическая дата, имя подтверждающего и причина проигрыша. Повторное открытие сохраняет историю. Импорт результатов из CRM не подключён и обозначен в UI. Задача «Выполнено» и прогноз AI не меняют результат сделки.

Аналитика использует период, события результатов и первый подтверждённый срок. Старые записи без подтверждения и истории исключаются из доли соблюдения срока с пояснением покрытия. Суммы и средние показаны отдельно по валютам, любой показатель открывает исходные записи. Определения — в `ANALYTICS_SPEC.md`, итог и ограничения — в `UI_REDESIGN_RESULT.md`.

Для отдельного синтетического стенда выполнить `scripts/preview_redesign.py`, затем запускать Streamlit с `CALLMIND_DATA_DIR=D:\hackaton\mts-callmind\.test-data\redesign` и `CALLMIND_TEST_MODE=1`. Первый параметр изолирует базу, второй помечает шапку «Тест». После изменений импортированных Python-модулей перезапустите Streamlit.

## Google Calendar

### Подключение кнопками в настройках

В начале «Настроек» есть отдельные кнопки **Подключить Bitrix24** и **Подключить Google Calendar**. Они открывают страницу сервиса в новой вкладке; CallMind принимает одноразовый ответ, проверяет доступ и хранит токен на сервере. Вернувшись, нажмите «Обновить состояние подключений». Подключение не переносит договорённости: сохранены отдельные действия после «Подтвердить». Кнопка ведёт на локальный обработчик начала входа: новый OAuth state и срок 10 минут создаются только при нажатии. Данные незавершённого входа, включая PKCE verifier, сохраняются в локальной SQLite. Повторный callback с тем же кодом показывает сохранённый результат без повторного обращения к провайдеру; другой код для использованного state отклоняется. Ошибка одного сервиса сохраняется отдельно от результата другого.

Перед первым использованием администратор регистрирует приложения. Пароли аккаунтов и секреты приложений не вводятся в интерфейс CallMind.

Это подготовка **команды CallMind**, а не каждого конечного пользователя. Пользователь подключает готовое приложение через OAuth-кнопку, входит на странице сервиса и разрешает доступ. Панель автоматически перечитывает локальный результат каждые 3 секунды; это не вызывает API провайдеров и не запускает перенос. Пока приложения не зарегистрированы, кнопки недоступны с пользовательским объяснением.

Для самостоятельного подключения разных клиентских порталов Bitrix24 нужно зарегистрировать распространяемое приложение, а не выдавать каждому пользователю инструкцию по созданию локального приложения. Оно должно быть установлено на портале до OAuth-входа; права установки регулирует Bitrix24. Отсутствие прав нельзя обойти API. Для Google публичный запуск также требует корректно опубликованного экрана согласия и выполнения требований Google к запрашиваемым разрешениям. Текущий код не регистрирует приложения во внешних кабинетах и не реализует вход пользователей CallMind или изоляцию их данных: общий демо-аккаунт нельзя выдавать за персональные подключения нескольких менеджеров.

* Google: включить Calendar API, настроить экран согласия и тестового пользователя. Для локального запуска подходят ключи Desktop app в `GOOGLE_CREDENTIALS_FILE`; callback `http://127.0.0.1:8766/oauth/google/callback`. Открывать в обычном браузере на компьютере с CallMind. Если задан `CALLMIND_OAUTH_PUBLIC_BASE=https://your-host`, нужны ключи Web application с точным разрешённым redirect URI `https://your-host/oauth/google/callback`.
* Bitrix24: зарегистрировать и установить OAuth-приложение на выбранном портале, предоставить права `task` и `user` для проверки текущего пользователя; задать `BITRIX24_CLIENT_ID` и `BITRIX24_CLIENT_SECRET`. Зарегистрированный адрес возврата: `https://your-host/oauth/bitrix24/callback`; установить `CALLMIND_OAUTH_PUBLIC_BASE=https://your-host` и настроить HTTPS reverse proxy `/oauth/` на `127.0.0.1:8766`. Bitrix24 берёт адрес возврата из регистрации приложения. В UI пользователь указывает только HTTPS-адрес облачного портала; произвольные/self-hosted адреса пока не поддерживаются.
* Порт обработчика задаётся `CALLMIND_OAUTH_PORT` (по умолчанию 8766). Обработчик запускается при подготовке доступной ссылки; занятый порт выдаёт ошибку, а не ложный результат подключения. После перезапуска в том же рабочем пространстве и на том же callback-порту незавершённый вход восстанавливается из SQLite. Если процесс прерван во время обмена кода, повторный обмен блокируется: нужно сверить состояние и при необходимости начать новый вход. Не выводить query strings callback/token endpoint в логи прокси: они содержат одноразовые коды или секреты.
* Токены записываются атомарно в `GOOGLE_TOKEN_FILE` и `BITRIX24_TOKEN_FILE` (по умолчанию внутри `data/`). На Windows ограничьте доступ к каталогу средствами ACL. Файлы исключены из Git; `chmod` сам по себе не обеспечивает Windows ACL. Обновление Bitrix24 выполняется при явном переносе; доступ ограничен правами вошедшего пользователя. Если `BITRIX24_RESPONSIBLE_ID` не указан, задачи назначаются вошедшему пользователю; явный ID сохраняет прежнее назначение.

Старый вебхук Bitrix24 и подключение Google через скрипт остаются рабочими. При наличии OAuth-токена Bitrix24 использует OAuth. Перед сменой аккаунта проверьте ранее созданные задачи: привязки зависят от аккаунта, автоматического переноса между аккаунтами нет. Эта версия имеет общие подключения для одного демо-аккаунта; публичное использование несколькими пользователями требует авторизации CallMind, изоляции токенов и записей. Обработчик OAuth и HTTPS-прокси сами по себе не реализуют такую модель доступа.

Реальный вход требует регистрации приложений и проверки на выбранных аккаунтах; автоматические тесты используют сетевые заглушки. Источники: [полный OAuth Bitrix24](https://apidocs.bitrix24.com/settings/oauth/index.html), [Google Desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app), [Google Web OAuth](https://developers.google.com/identity/protocols/oauth2/web-server).

1. В Google Cloud включить Calendar API, настроить OAuth consent screen и тестового пользователя, создать OAuth client типа **Desktop app** для локальной демонстрации.
2. Скачать JSON как `credentials-google.json` или указать путь в `GOOGLE_CREDENTIALS_FILE`.
3. Выполнить:

```powershell
.venv-ui/Scripts/python.exe scripts/connect_google.py
```

4. Открыть выведенную ссылку самостоятельно, разрешить доступ и дождаться локального callback. Токен сохраняется на сервере; приложение обновляет истёкший access token при наличии refresh token.
5. В настройках оставить календарь `primary` или указать ID доступного календаря и интервал popup-напоминаний. Отправлять только после проверки, кнопкой «Подтвердить» и выбранной кнопкой переноса.

Встреча создаёт приватное событие с занятостью и длительностью из настроек; её срок трактуется как начало. Задача создаёт приватное напоминание «Напоминание: …» без занятости: при точном сроке — минутный маркер, без времени — запись на весь день. Это событие Calendar API, не Google Tasks. Время all-day уведомлений определяет календарь. Те же правила действуют в ICS. При следующем ручном переносе выполненная задача отменяет напоминание, возврат пытается восстановить его; выполненная встреча остаётся в истории без напоминания. Удаление срока отменяет ранее отправленное событие при следующем ручном переносе. Внешнее удаление может требовать ручного восстановления.

Для одной договорённости используется стабильный event ID, что позволяет повторять запрос без нового события. Смена календаря создаёт запись в новом календаре; ранее созданные объекты не удаляются автоматически. На сервере для нескольких пользователей нужен отдельный web OAuth flow и раздельное хранение токенов: этот Desktop flow предназначен для одного локального демо-аккаунта.

OAuth запрашивает управление событиями и чтение сведений о календарях для определения стабильного ID аккаунта. Старый токен, не содержащий второй scope, нужно обновить через повторное подключение. После появления звонков смена часового пояса блокируется до миграции существующих дат, чтобы не изменить их смысл.

## API для команды

```powershell
.venv-ui/Scripts/python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

Все запросы требуют заголовок `X-API-Key`, совпадающий с `CALLMIND_API_KEY`; без конфигурации API закрыт. Доступны GET `/calls`, `/calls/{id}`, `/clients`, `/agreements`, `/settings`; PATCH `/calls/{id}`, `/agreements/{id}`, `/agreements/{id}/status`; PUT `/settings`; POST `/agreements/{id}/sync/bitrix24` и `/sync/google`.

Модель договорённости: ID, описание, ответственная сторона (`manager/client/unknown`), ISO deadline/null, date_only, priority (`low/normal/high`), kind (`task/meeting`), status (`pending/done`), evidence. Ответы содержат состояния интеграций. Полный PATCH передаёт редактируемые поля целиком. Перед явным POST синхронизации пользователь подтверждает проверку через POST `/agreements/{id}/review`; без актуальной проверки сервер отклоняет отправку до сетевого запроса.

UI пока использует общий сервис хранения напрямую, API предназначен для других клиентов и будущего отделения frontend. API не является реализацией телефонного webhook и не запускает обработку потока аудио. Не публиковать UI/API в интернет без пользовательской авторизации, TLS и разделения доступа.

## Проверка

```powershell
.venv-ui/Scripts/python.exe -m unittest discover -s tests -v
```

Тесты работают на временной SQLite и синтетическом аудиофайле, с подменёнными сетевыми ответами. Они не вызывают Gemini, Bitrix24 или Google и не изменяют рабочую базу. Реальные интеграции требуют проверки после настройки аккаунтов; мобильная компоновка требует проверки на iOS/Android.

## Что ещё остаётся по ТЗ

Получение телефонного аудио без ручной загрузки, обработка во время звонка, измерение 90% распознавания ключевых фраз, полноценные правила распознавания, Qwen/обучение, роли команды, шифрование и аудит доступа. Настройки текущего интерфейса регулируют задачи и интеграции, но не заменяют обучение или правила распознавания AI. Согласие в форме загрузки — подтверждение пользователя, а не реализация телефонного уведомления сторон.

Источники: [Bitrix24 webhooks](https://apidocs.bitrix24.ru/local-integrations/local-webhooks.html), [создание задач](https://apidocs.bitrix24.ru/api-reference/tasks/tasks-task-add.html), [Google OAuth quickstart](https://developers.google.com/workspace/calendar/api/quickstart/python), [Google events](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert).
