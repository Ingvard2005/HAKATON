# Аудит CallMind AI: трек 2, фиксация договорённостей

Дата: 6 октября 2026 года. Проверено текущее содержимое рабочей папки, включая незакоммиченные изменения.

## Вывод

В проекте реализовано ядро прототипа: загрузка записи → Whisper → анализ Gemini → сохранение звонка и договорённостей → просмотр истории и изменение статуса. Это полезная основа, но обязательные требования выбранного трека полностью пока не подтверждены. Главные пробелы: получение звонка автоматически и обработка во время разговора, CRM и календарь, мобильный сценарий, настройки, безопасность и измеренная точность.

Переход на локальную Qwen помогает организовать обработку текста внутри своего контура. Он сам по себе не закрывает эти пробелы и не улучшает распознавание аудио.

## 3. Исправления в существующем коде

### Критично до демонстрации

1. **Секрет и данные уже отслеживаются Git.** В `git ls-files` присутствуют `.env`, `data/callmind.db`, сохранённая запись, `.idea` и `__pycache__`. В `.env` есть непустой `GEMINI_API_KEY`, значение не выводилось. `.gitignore` не убирает ранее добавленные файлы. Удалить секрет и пользовательские данные из отслеживания, добавить `.env.example`. Если ключ передавался другим или репозиторий публиковался — заменить ключ; удаление из текущего дерева не удаляет его из истории. Переписывание истории согласовать с командой.
2. **Перепутаны вкладки Dashboard.** `frontend/app.py:654`: «Ожидаем клиента» выводит `today_items`; `:671`: «Просрочено» выводит `waiting_client`; `:690`: «Сегодня» выводит `done`; обработчика пятой вкладки «Выполнено» нет. `overdue` вычисляется, но не выводится. Исправить соответствие всех пяти вкладок и пустых состояний.
3. **Повторяются ключи кнопок Streamlit.** `frontend/app.py:213` и `:230`: ключ состоит только из статуса и ID. Одна активная задача может попасть одновременно в несколько вкладок, а содержимое вкладок создаётся при одном выполнении страницы. Это создаёт риск DuplicateElementKey; после исправления списков добавить контекст раздела/вкладки в ключ.
4. **Разные клиенты могут объединиться.** `services/storage.py:34`: если новый телефон не найден, поиск продолжается по имени. Синтетическая проверка подтвердила возврат существующего клиента с другим телефоном. При заданном новом телефоне не объединять по имени; нормализовать номера и определить политику уникальности. Без телефона одинаковое имя не считать надёжным идентификатором.
5. **Запуск в текущем окружении не воспроизводится.** `.venv` ссылается на недоступный базовый Python. Создать воспроизводимое окружение и инструкцию запуска, отдельно закрепить версии runtime и модель.

### Качество данных и устойчивость

6. **Сроки допускают некорректные значения.** `Agreement.deadline` в LLM-схеме — произвольная строка; `services/storage.py:22` превращает невалидную дату в None без предупреждения. Ошибка модели становится «срок не указан». Нужна явная ошибка валидации или статус «требует уточнения».
7. **Не определена семантика даты без времени.** `2026-10-06` сохраняется как полночь, а Dashboard сравнивает её с текущим временем. Задача «до сегодняшнего дня» может считаться просроченной с начала дня. Различать срок-день и срок-время; согласовать включительность и конец рабочего/календарного дня.
8. **Нет единого часового пояса.** Используются datetime.now(), naive даты и parser, принимающий offsets. Не гарантирован смысл времени между системами; возможен TypeError при сравнении aware/naive значений вне нормализованного хранения. Задать часовой пояс и правила сериализации для БД, календаря, CRM и модели.
9. **Ответственный определяется без говорящих.** Whisper сохраняет только текст, LLM получает цельную строку. На реплике «я пришлю» часто нельзя определить сторону. Для двухканального аудио использовать каналы; иначе рассмотреть диаризацию и отдельно установить роли — speaker_0 не означает автоматически менеджера. Оставлять unknown при недостатке данных.
10. **Цитаты не проверяются.** JSON-валидация проверяет форму, но не наличие evidence в транскрипции. Нужна проверка цитаты/диапазона, связь с сегментом и временем, предупреждение о неподтверждённом извлечении.
11. **Нет различения обещания, пожелания и отмены.** Добавить случаи «возможно пришлю», «не отправляйте», условные обязательства, перенесённые сроки, отменённые встречи. Связывать новые звонки с уже существующими обязательствами, исключать дубли.
12. **Нет ручной корректировки.** Разрешить исправить текст, срок, описание и ответственного; сохранять оригинал и журнал правок; повторный анализ не должен терять выполненные статусы или создавать дубликаты.
13. **Побочные действия при импорте.** WhisperModel и genai.Client создаются при импорте, поэтому просмотр истории зависит от инициализации AI. В Streamlit нет явного cache_resource для Whisper. Вынести ленивую/кэшируемую загрузку или отдельный процесс.
14. **Обработка блокирует интерфейс.** Нет job ID, статусов обработки, очереди, восстановления после сбоя, отмены, отдельного тайм-аута приложения. Для нескольких пользователей вынести тяжёлые задачи из UI.
15. **Аудио и БД не сохраняются атомарно.** Копия аудио создаётся до commit; при ошибке может остаться файл без записи БД. Добавить очистку при сбое и сверку файлов с БД.
16. **Нет идемпотентности.** Повторная загрузка или повторный webhook создаст новый звонок/задачи. Нужен external_call_id, уникальные ограничения и безопасное повторное выполнение; хеш файла может помогать, но не заменяет ID звонка.
17. **Статусы не ограничены на уровне сервиса.** set_agreement_status принимает любую строку. Добавить допустимые статусы, проверку переходов и completed_at. Без completed_at невозможно честно рассчитать выполнение вовремя.
18. **Нет миграций БД.** create_all создаёт таблицы, но не обновляет существующую схему при добавлении колонок. Нужны версионированные миграции и резервная копия перед изменением данных.
19. **Идентификаторы выбираемых клиентов могут потеряться.** В UI options — словарь по имени и телефону. Совпадающие подписи перезапишут элементы; использовать ID как значение и устойчивую подпись.
20. **Риски истории могут устаревать.** Результат хранится только в session_state и не инвалидируется при добавлении звонка/изменении задачи. Сохранять дату анализа, версию модели, версию входных данных; не трактовать неизвестность выполнения как доказательство невыполнения.
21. **История отправляется модели целиком.** analyze_client_history собирает все транскрипции. Для Qwen учитывать лимит токенов, резерв ответа, выбор релевантных звонков, структурированные состояния задач и обработку длинной истории.
22. **Транскрипция может содержать инструкции модели.** Отделить system-инструкции от анализируемых данных, не исполнять указания из разговоров, проверить adversarial-примеры. Структурированный JSON не предотвращает смысловую подмену.
23. **Недостаточная проверка входа.** Есть фильтр расширений, но нет явной политики длительности/размера, проверки декодирования, пустой речи и повреждённого аудио. Добавить ограничения и понятные ошибки.
24. **Нет управления записями и удаления.** Предусмотреть безопасное удаление/экспорт данных клиента, срок хранения аудио и транскриптов, минимизацию содержания технических логов.

## 4. Переход на Qwen3-8B-Q4_K_M

### Что именно заменяется

Текущая цепочка: аудио → faster-whisper small → текст → Gemini → структурированный результат. После замены: аудио → ASR → текст → локальная Qwen3 → тот же контракт данных.

Qwen3-8B — текстовая модель. Whisper остаётся отдельным компонентом: проблемы распознавания чисел, имён и ключевых фраз требуется измерять и исправлять на уровне ASR/аудио.

### Правильный путь обучения

Q4_K_M — вариант квантования GGUF для исполнения в llama.cpp и совместимых средах. Для стандартного LoRA/QLoRA-процесса брать исходную `Qwen/Qwen3-8B`, а не готовый GGUF. 4-битная загрузка при QLoRA и GGUF Q4_K_M — разные этапы и форматы.

1. Запустить исходную Qwen3-8B-Q4_K_M без дообучения и получить baseline на ваших эталонах.
2. Собрать обезличенные пары «дата звонка + расшифровка → проверенный человеком JSON», включая отсутствие договорённостей и сложные случаи.
3. Разделить train/validation/test по клиентам/сценариям; фрагменты одного звонка не должны попадать по разные стороны разделения.
4. Провести supervised fine-tuning исходной Qwen3-8B через LoRA или QLoRA. Инструмент и параметры выбрать после проверки GPU и памяти.
5. Проверить адаптер на отложенном наборе, объединить с исходной моделью при выбранном процессе экспорта, конвертировать в GGUF и квантовать в Q4_K_M.
6. Повторно проверить именно конечную квантованную модель, включая скорость и стабильность JSON. Оставить дообучение только при измеренном улучшении.

В репозитории сейчас нет датасета, разметки, обучающего кода, адаптеров, checkpoint, оценки или GGUF-файла. Утверждать, что обучение уже подготовлено, нельзя.

### Изменения приложения

- В `services/llm.py` заменить Google SDK на адаптер локального сервера. Сохранить интерфейсы analyze_call/analyze_client_history, вынести схемы из реализации провайдера.
- Для выбранного GGUF использовать llama.cpp или совместимый runtime. Указать URL, модель, лимиты контекста/ответа и тайм-ауты через конфигурацию; зафиксировать версию runtime.
- Передавать JSON Schema способом, поддерживаемым конкретным сервером, и независимо проверять ответ Pydantic. Добавить ограниченные повторы при неправильном формате; возвращать объяснимую ошибку после исчерпания повторов.
- Настроить non-thinking для извлечения, проверить чат-шаблон и отсутствие `<think>` в JSON. Точный переключатель зависит от runtime; параметр Transformers нельзя автоматически переносить на любой HTTP-сервер.
- Проверять также смысл: цитату, ответственного, дату, отсутствие неподтверждённых полей. Для суммы/валюты/приоритета сначала определить расширенный контракт данных.
- Добавить версии модели, промпта, схемы и время обработки к сохранённому результату.
- Переписать оба AI-сценария, тексты Gemini в интерфейсе и ручных скриптах; убрать обязательный Google-ключ и не делать скрытый fallback во внешний API.
- Разделить зависимости inference и обучения. Наличие httpx позволяет строить HTTP-адаптер; новый SDK необязателен.
- Проверить весь локальный путь: аудио, ASR, текстовый анализ, хранилище, логи, резервные копии. Локальная LLM не добавляет авторизацию, шифрование и аудит автоматически.

### Данные и метрики

Предлагаемый старт, не требование ТЗ: 50–100 размеченных звонков/сценариев для первичного baseline, затем расширение набора по обнаруженным ошибкам. Объём обучающего набора определяется разнообразием случаев и learning curves, а не обещанием фиксированного процента качества.

Обязательные группы примеров: «завтра»/«через 3 дня»/«до пятницы»; дата без времени и время без даты; суммы и валюты; несколько говорящих; шум/перебивания; отрицания; пожелания без обещания; условное обещание; перенос/отмена; несколько обязательств; повторное обещание; выполненная задача; звонок без договорённостей; неоднозначный ответственный; попытка инструкций внутри разговора.

Измерять отдельно:

- ASR: распознавание размеченных ключевых фраз, ошибки чисел/дат/имён; WER как дополнительную метрику. Порог 90% в ТЗ нельзя автоматически заменить общим показателем WER или валидностью JSON.
- Извлечение: precision/recall/F1 договорённостей; правильность ответственного и нормализованного срока; подтверждённость цитат; долю выдуманных обязательств.
- Формат: долю ответов, проходящих схему, до и после повторов.
- Производительность: длительность ASR/LLM/всей цепочки, p50/p95, память и параллельные звонки на целевом устройстве.
- Интеграции: успешное создание/обновление внешней задачи, отсутствие дублей, восстановление после недоступности CRM.

Характеристики GPU и RAM не проверены. Размер весов не равен памяти исполнения: нужны дополнительные ресурсы для KV-cache, контекста, ASR и параллельных запросов. Скорость и затраты обучения оценить после выбора железа, длины контекста и batch size.

|---|---|---|

| P1 | По одной интеграции CRM и календаря | Созданные задачи/события видны во внешней системе; повтор webhook безопасен |

| P2 | LoRA/QLoRA, экспорт, сравнение до/после | Конечный Q4_K_M улучшает метрики на отдельном test, а не только обучающих примерах |
| P2 | Команда, роли, отчёт руководителя, экспорт, расширенная аналитика | Данные разделены по менеджерам; KPI выполнения вычисляются по реальному completed_at |

Для защиты подготовить последовательный показ: тестовый звонок → автоматическая фиксация → проверяемые фрагменты и сроки → исправление ошибки → задача CRM и событие календаря → уведомление → выполненная задача и KPI. Показ ручной загрузки сам по себе не подтверждает автоматизацию во время звонка.

## 6. Что показать по готовности к МТС

Лекция, страницы 10–13: согласия и уведомления, модель доступа и аудит, локальный контур обработки, SIP/VoIP, интеграция с каналами МТС и CRM/BSS, тарификация через баланс, масштабирование и экономика. Это описание ожиданий конкурса, а не юридическое заключение о применимости конкретных норм.

На странице 12 прямо допускается прототип на одном облачном API и тестовом номере при объяснении промышленной архитектуры. Значит, промышленную доступность 99,9%+ и сотни тысяч пользователей не нужно выдавать за уже достигнутые показатели хакатонного MVP. При этом обязательные продуктовые требования второго трека перечислены отдельно и ожидаются в прототипе.

Предлагаемая архитектура: голосовой источник оператора → приём фрагментов/записей → очередь заданий → ASR → Qwen → проверка результата → хранилище → CRM/календарь/уведомления → мобильный интерфейс. Streamlit можно сохранить для демонстрации и внутреннего управления; серверные интеграции отделить от UI.

Подготовить схему размещения и границ доступа; перечень открытых вопросов оператору по голосовому источнику, уведомлениям и хранению; предполагаемый тариф; расчёт себестоимости минуты/звонка на основании реального benchmark; план резервирования и роста нагрузки. Подписка или оплата по минутам — гипотезы для расчёта, не готовая финансовая модель.
