# CallMind ↔ Bitrix24

Реализовано в Streamlit и существующем API. Таблицы добавляются через `init_db`, существующие записи, экспорт, история и OAuth-подключения сохраняются. Проверки используют временную SQLite и сетевые заглушки; реальные записи клиентов в CRM не отправлялись.

## Пользовательский сценарий

1. Подключить Bitrix24 в настройках; нужны разрешения `crm`, `task`, `user`.
2. В «Клиенты» проверить имя, телефон/email, компанию (ID существующей компании), менеджера (ID пользователя CRM). Если найдено несколько контактов, выбрать ID нужного контакта. Сопоставление только по имени запрещено.
3. При необходимости получить сделки связанного клиента из CRM. В деталях договорённости выбрать сделку и исполнителя CRM. Сторона обещания и исполнитель задачи — разные поля.
4. Сохранить и подтвердить договорённость. Нажать «Перенос в CRM» либо «Перенос» для обоих сервисов. До этого автоматическое создание контакта/задачи не выполняется.
5. По желанию включить «Автоматически синхронизировать связанные записи Bitrix24». Переключатель по умолчанию выключен. Новые несвязанные записи фоновый процесс не создаёт.

## Поля и направления

| Объект | Поля | Направление |
|---|---|---|
| Контакт | Имя NAME, основной рабочий телефон/email, компания COMPANY_ID, менеджер ASSIGNED_BY_ID | В обе стороны |
| Задача | Заголовок, срок, приоритет, исполнитель, выполнена/в работе, связанный контакт и выбранная сделка | В обе стороны для известных связей |
| Задача | Цитата, сторона обещания, локальный идентификатор договорённости | В описание при первом переносе; свободный текст CRM не заменяет доказательства CallMind |
| Сделка | Название, сумма/валюта, стадия, менеджер, подтверждённый результат | Из CRM в CallMind |

Другие телефоны/email, фамилия и отчество существующего контакта сохраняются. Компания автоматически не создаётся. Пустое значение менеджера не означает удаление пользователя в CRM; при отказе сервиса сохраняется ошибка.

Статус задачи нормализуется: только статус Bitrix24 `5` означает «Выполнено», остальные — «В работе». Приоритеты: 0/1/2. Срок без времени передаётся как 23:59 указанной даты; отсутствие срока очищает DEADLINE. В обратном направлении признак «без времени» сохраняется, если CRM сохранила эту конвенцию. Точное время завершения задачи берётся из CLOSED_DATE; при отсутствии неизвестно и не подменяется временем сверки.

Завершение задачи не закрывает сделку. Семантика стадии сделки P/S/F означает в работе/успех/проигрыш. Источник — CRM, время — MOVED_TIME, либо DATE_MODIFY при отсутствии времени смены стадии; интерфейс явно обозначает это ограничение. Причина проигрыша из предположения не создаётся. Более новое человеческое подтверждение, расходящееся с CRM, требует проверки и не затирается.

В списке клиентов доступны телефон, email, компания/менеджер ID, состояние CRM. В списке задач — действие, клиент/сторона, срок, статус, исполнитель/сделка и состояние CRM для связанных задач. В деталях сделки — сумма/валюта, стадия/менеджер, результат/источник/время, связанные записи. ID служат рабочим вариантом выбора до реализации справочников пользователей и компаний.

## Сверка, ошибки и история

Связи хранятся отдельно для каждого портала, по ID внешней записи. Каждая сверка сравнивает локальные значения, CRM и последнее согласованное состояние. Изменения разных полей объединяются. Разные изменения одного поля показывают оба значения и требуют выбора пользователя. Перед выбором проверяется актуальность значений.

Изменённые действие/срок договорённости требуют нового человеческого подтверждения перед отправкой. Приём правок из CRM также может сделать подтверждение неактуальным; перед следующей отправкой потребуется проверка. Неизвестная сделка или другой контакт у задачи не привязывается автоматически.

Обновления отправляют только изменённые поля. Внешняя запись перечитывается непосредственно перед отправкой и после неё. REST Bitrix24 не предоставляет использованному здесь методу атомарного compare-and-swap: изменение ровно между проверкой и записью нельзя полностью исключить. Требуется стабильный сервер и дальнейшее развитие событийной синхронизации для промышленной нагрузки.

ID созданной записи сохраняется до проверочного чтения. Если ответ на создание не получен, повтор блокируется до ручной привязки ID; это защищает от дублей. Удалённая/недоступная внешняя запись не удаляет локальную историю и не создаётся заново автоматически. Ошибка одной записи не останавливает остальные. Источник и изменения записываются в человеческий журнал.

## Фоновая работа и ограничения

Встроенный процесс сверяет связанные записи каждые 30 секунд при включённой настройке и работающем приложении/API. В тестовом режиме встроенный процесс отключён. Для постоянной работы: отдельный процесс `.venv-ui/Scripts/python.exe tools/crm_worker.py` с тем же DATA_DIR и серверными OAuth-настройками. После закрытия обоих процессов синхронизация прекращается. По умолчанию не запускается регистрация обработчиков событий CRM; временный HTTPS-туннель обслуживает только OAuth callback.

Обновление календаря: реализована отдельная двусторонняя сверка и независимый переключатель, описанные в [CALENDAR_SYNC_SPEC.md](CALENDAR_SYNC_SPEC.md). Первый перенос остаётся явным. Если CRM изменила связанную договорённость, прежний календарный перенос помечается устаревшим; перед исходящей записью изменённого действия/срока нужна проверка человека. Правила «встреча → событие», «задача → прозрачное напоминание по сроку» сохраняются.

Обратная синхронизация заголовка задачи поддерживается для шаблона `{description}`. Для других шаблонов требуется ручная проверка: невозможно безопасно восстановить действие из произвольного заголовка.

Синхронизация клиентов/задач реализована; двусторонняя запись стадий/сумм сделки, корпоративный доступ, справочники компаний/исполнителей и непрерывная работа на сервере остаются отдельными зависимостями.

## Проверка

`.venv-ui/Scripts/python.exe -m unittest discover -s tests -t .`

Тесты проверяют тристороннюю сверку, конфликты/устаревший выбор, дедупликацию, блокировку неопределённого создания, сохранность дополнительных телефонов, завершение без выдуманного времени, подтверждение перед отправкой, привязку сделки и выключенную фоновую сеть. Реальные HTTP-запросы в новых CRM-тестах запрещены.

Официальные поля: [tasks.task.get](https://apidocs.bitrix24.com/api-reference/tasks/tasks-task-get.html), [поля задач](https://apidocs.bitrix24.com/api-reference/tasks/tasks-task-get-fields.html), [crm.deal.get](https://apidocs.bitrix24.com/api-reference/crm/deals/crm-deal-get.html). UF_CRM_TASK запрашивается явно: стандартное чтение задачи его не возвращает.
